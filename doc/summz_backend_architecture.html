🔐 Authentication Architecture Two independent auth layers
Layer 1 — Cloud Run IAM
Deployed with --no-allow-unauthenticated. Cloud Run requires a valid Google identity token on every inbound request before it reaches Express.

For local testing use gcloud auth print-identity-token.
Note: mobile/web clients cannot obtain a Google identity token. If clients call this API directly, switch to --allow-unauthenticated and rely on Layer 2.
Layer 2 — Firebase Middleware
verifyFirebaseToken.ts applied to all /auth/* and /user/* routes.

Reads Authorization: Bearer <firebase-id-token> → calls firebase.auth().verifyIdToken() → extracts decoded.uid → sets req.user.firebase_uid.

All downstream DB queries scope data by firebase_uid.
Firebase Admin init — key detail
FIREBASE_PRIVATE_KEY newline handling: The PEM key is stored in Secret Manager with literal \n escape sequences (two chars). lib/firebase.ts calls .replace(/\\n/g, '\n') before passing to the SDK, converting them to real newlines. Cloud Run injects the secret value as-is — no extra escaping needed.

🗄️ Database Architecture Supabase (PostgreSQL) — service role, bypasses RLS
Design decision: The backend uses SUPABASE_SERVICE_ROLE_KEY which bypasses all RLS policies. The API itself enforces authorization — callers are scoped to their own firebase_uid by the middleware. users.firebase_uid is TEXT (not a Supabase UUID) and maps 1:1 to Firebase Auth UIDs.

💡 Key Design Decisions & Gotchas Things that are easy to get wrong
1
Clients never call Supabase directly
All DB access is proxied through this API. RLS is bypassed via service role key — the only auth that matters is the Firebase token the middleware validates. This means no RLS debugging, and one clear security boundary.
2
firebase_uid is TEXT, not a Supabase UUID
Firebase Auth UIDs are opaque strings (e.g. abc123xyz). Using them directly as the user PK avoids a mapping layer. All user-scoped tables reference firebase_uid TEXT.
3
Manual gcloud builds submit requires --substitutions
$COMMIT_SHA is only auto-populated by GitHub triggers. For manual builds always pass: --substitutions=COMMIT_SHA=$(git rev-parse HEAD). Without it the Docker tag becomes :"" and fails immediately.
4
Secret values must be plain text — no JSON quotes
If you copy a value from a JSON file (e.g. a service account JSON), the value may be wrapped in "...". Cloud Run injects those quotes literally into the env var, breaking the secret. Store and verify using gcloud secrets versions access latest --secret=NAME.
5
Both .gcloudignore AND .dockerignore must include src/ and tsconfig.json
.gcloudignore controls what gets uploaded to GCS (= Docker build context). If it excludes src/ or tsconfig.json, the Docker builder stage fails. .dockerignore must also not exclude src/ since the builder stage needs it to compile TypeScript.
6
Cloud Run reserves PORT — do not inject it as a secret
Cloud Run sets PORT=8080 automatically. Adding it to --set-secrets causes a deployment error: "The following reserved env names were provided: PORT". Same for NODE_ENV — set in the Dockerfile instead.
7
Two service accounts need Secret Manager access
The Cloud Build SA needs secretmanager.secretAccessor to run the deploy command. The Cloud Run compute SA (PROJECT_NUMBER-compute@developer.gserviceaccount.com) also needs it so the container can read secrets at startup. Missing the second one causes a revision startup failure.
